# sigrok driver for the gusmanb LogicAnalyzer

A libsigrok driver (`gusmanb-logicanalyzer`) for
[gusmanb/logicanalyzer](https://github.com/gusmanb/logicanalyzer) devices
(Pico, Pico 2, Pico W, Zero) running **stock firmware V6_0**. With it,
**PulseView** and **sigrok-cli** can capture from the device over USB.

It targets the **libsigrok 0.5.2** release (the version Arch ships) and
also compiles against current libsigrok master without changes.

## Layout

| Path | What |
|---|---|
| `src/hardware/gusmanb-logicanalyzer/` | **the driver** (`api.c`, `protocol.c`, `protocol.h`), laid out as in the libsigrok tree. This is the only copy to edit |
| `patches/0001-gusmanb-logicanalyzer-driver.patch` | the driver as one patch against libsigrok 0.5.2 (generated by `tools/make-patch.sh`) |
| `packaging/` | Arch `PKGBUILD` (`libsigrok-gusmanb`, replaces `libsigrok`), Arch's own patches and a copy of the driver patch |
| `tools/prepare-libsigrok.sh` | sets up `build/libsigrok-<version>` with the driver registered and copied in |
| `tools/build-dev.sh` | builds 0.5.2 with the driver and installs it into `~/.local/sigrok` |
| `tools/make-patch.sh` | regenerates the patch and updates the PKGBUILD checksum |
| `tools/check-master.sh` | compiles the driver against current libsigrok master |
| `tools/sigrok-cli-gla`, `tools/pulseview-gla` | run the installed tools with that library |
| `tools/fake_gla.py` | fake device on a pseudo-terminal (protocol emulator) |
| `tools/test_driver.py`, `tools/run-tests.sh` | end-to-end tests via sigrok-cli |
| `tools/build-test-libserialport.sh` | builds the test-only libserialport the fake-device tests need |
| `tools/stoptest.c` | stops a capture with `sr_session_stop()`, like PulseView's Stop button |
| `tools/ftdi_sig.py` | drives a USB-UART adapter (TX/RTS/DTR) as a test signal source |
| `PLAN.md` | design plan and protocol notes |
| `build/` | (ignored) libsigrok/libserialport clones, build trees, test libraries |

The scripts clone libsigrok and libserialport from sigrok.org on first
use. To clone from local mirrors instead, set `LIBSIGROK_GIT` /
`LIBSERIALPORT_GIT`.

### Development cycle

1. Edit `src/hardware/gusmanb-logicanalyzer/*`.
2. `tools/build-dev.sh` (copies the sources into the build tree, builds, installs).
3. `tools/run-tests.sh`, and a capture on hardware.
4. `tools/make-patch.sh` (updates `patches/` and `packaging/`), then commit.
5. Now and then, `tools/check-master.sh`.

## Quick start

Build and install into `~/.local/sigrok`. Nothing system-wide is touched.

```bash
tools/build-dev.sh --reconf
```

Then plug in the analyzer. It appears as `/dev/ttyACM0`, which your user
can open because it is in the `uucp` group. **No port needs to be given:**
the driver finds analyzers by their USB ID (`1209:3020`). Add
`:conn=/dev/ttyACMn` to pick one explicitly.

```bash
tools/sigrok-cli-gla -d gusmanb-logicanalyzer --show
```

```bash
tools/sigrok-cli-gla -d gusmanb-logicanalyzer --channels D0,D1,D2,D3 --config samplerate=10m --samples 100000 --config captureratio=10 --triggers D0=r -o capture.sr
```

```bash
tools/pulseview-gla
```

In PulseView, open *Connect to Device*, choose **gusmanb LogicAnalyzer**
and click *Scan for devices*. The interface choice can stay at its
default; you only need *Serial Port* to force a specific port.

A port that another program has open (e.g. a running PulseView) can't be
probed: libsigrok logs "Device or resource busy" and the scan finds
nothing.

To use the driver from the normal menu entries (without the wrappers),
build and install the package. This replaces Arch's `libsigrok`, and needs
the same make-dependencies as Arch's package (Java, Ruby, SWIG):

```bash
cd packaging && makepkg -si
```

## How sigrok settings map onto the device

| sigrok | Device |
|---|---|
| Channels D0–D23 | analyzer channels 0–23 |
| samplerate | 5 kHz (10 kHz on turbo builds) up to `FREQ` (100 or 200 MHz). Any rate in that range works (fractional divider), and 1-2-5 steps are listed. Choosing the **last listed rate (`BLASTFREQ`) selects blast mode** |
| limit_samples | the maximum depends on the **highest enabled channel**: up to D7, D15 or D23 → buffer / 1, 2 or 4. On the Pico 2 that is 393216, 196608 or 98304 samples |
| captureratio | pre-trigger share, clamped to 2 … 10 % of the buffer (same limit as the official app) |

### Triggers

**No trigger → the capture starts immediately.** The firmware itself has
no untriggered mode, so the driver triggers on "EXT input low" (trigger
channel 24, GPIO1). That pin idles low (pull-down, wired to the idle
trigger output GPIO0), so the level-sensitive trigger fires at once. These
captures have no pre-trigger part and no trigger marker. *If you drive the
EXT input to chain analyzers, an untriggered capture waits for it to go
low.*

| You configure | Hardware trigger used |
|---|---|
| One channel `1`/`r` (D0–D23) | edge trigger, high |
| One channel `0`/`f` (D0–D23) | edge trigger, low |
| Several channels, all `0`/`1`, **consecutive**, ending at D4 or below | fast pattern trigger (≤ 5 bits) |
| Several channels, all `0`/`1`, consecutive, within D0–D15 | complex pattern trigger (≤ 16 bits) |
| Anything else (edges in a pattern, gaps, above D15, several stages) | rejected with an error |

Notes:
- The "edge" trigger is **level sensitive**: it fires as soon as the pin
  has the level. A rising trigger on a line that is already high fires
  immediately.
- **Pattern triggers need GPIO0 and GPIO1 shorted** on the Pico (they are
  connected on the official PCB).
- The driver moves the trigger point to compensate the trigger latency
  (3 cycles for fast, 5 for complex), the same correction the official
  app makes.
- **Blast mode** supports single-channel triggers only and has no
  pre-trigger samples.
- Burst/loop capture is not supported (sigrok has no equivalent).

### Behaviour differences from a typical sigrok analyzer

- Data appears **after** the capture is complete. There is no streaming.
- **Stop** while waiting for the trigger takes up to about 2.5 s: the
  firmware checks for a cancel only once a second.
- `sigrok-cli` 0.7.2 has no Ctrl-C handler. Ctrl-C kills it and leaves
  the device armed. The next scan or capture cancels the armed capture
  automatically, which takes about 1 extra second.

## Firmware 6.0 quirks handled or worked around

- **Text replies end in `\r\n`** (Pico SDK stdio). The driver skips the
  empty "lines" this creates, and consumes the `\n` after
  `CAPTURE_STARTED` so it isn't read as the first byte of the sample count.
  *Found on hardware.*
- **Frame parser can get stuck.** If a capture is armed when the host
  program dies (e.g. Ctrl-C in sigrok-cli), the next frame's first byte is
  consumed as the cancel request. Its trailing `AA 55` then leaves the
  parser holding a stray `0x55`, and from then on **every** command is
  rejected: the device looks dead until it is replugged. The driver sends
  an `AA 55 00` resync preamble before every command, which recovers from
  this and every other parser state. *Found on hardware; the official app
  has the same exposure.*
- **Blast-mode off-by-one** (confirmed on hardware): the firmware sends the
  blast buffer shifted by one sample, with a bogus last sample. The driver
  requests one extra sample and drops the bogus one.
- **DTR:** the Pico's USB stdio sends nothing unless DTR is asserted. The
  default `serialcomm` is `115200/8n1/dtr=1/rts=1`.
- **Burst-measure hang** (`measure=1` with `loopCount=0`): avoided, since
  the driver always sends `loopCount=0`, `measure=0`.
- **Capture latency:** the firmware's main loop checks for a finished
  capture only every 2 s, so even an instantly triggered capture takes
  about 2 s.
- Checked and **not** a problem: the blast trigger pin's input inversion
  does not leak into the next capture.

## Testing without hardware

```bash
tools/build-test-libserialport.sh
```

```bash
tools/run-tests.sh
```

Stock libserialport 0.1.x cannot open pseudo-terminals.
`build-test-libserialport.sh` builds a **test-only** copy into
`build/testlibs` that allows them. It is loaded only by `run-tests.sh`;
never install it.

The fake device models the physical inputs as a 24-bit counter whose value
at the trigger sample is `0x100000`. The tests check every captured sample,
the trigger position, the request the driver sends, and the error and stop
paths.

To try it interactively:

```bash
python3 tools/fake_gla.py --trigger-delay 1
```

Then use the printed `/dev/pts/N` with
`LD_LIBRARY_PATH=build/testlibs/lib tools/sigrok-cli-gla -d gusmanb-logicanalyzer:conn=/dev/pts/N:serialcomm=115200/8n1 ...`.
`serialcomm` without DTR is needed because pseudo-terminals have no modem lines.

## Hardware tests (Pico 2, 2026-11-07)

Signal source: FT232R at 3.3 V, TX→D0, RTS→D1, DTR→D2, GND→GND, driven by
`tools/ftdi_sig.py` (RTS/DTR are given as pin levels).

| Test | Result |
|---|---|
| `--show` | `PICO_2 V6_0`, 24 ch, 393216 B buffer, 100 MHz / 200 MHz blast |
| Static levels | TX→D0, RTS→D1, DTR→D2 mapped correctly |
| Rising (1 MHz) / falling (10 MHz) edge | transition exactly at sample 200 = 10 % marker |
| UART 115200 decode (8, 16 and 24-channel modes) | all strings decoded correctly |
| Fast pattern `D1=1,D2=0` (1 and 100 MHz) | transition at the marker |
| Complex pattern D1–D5 (1 and 100 MHz) | within ±1 sample of the marker |
| Blast 200 MHz, rising D1 | all samples valid; bogus last sample confirmed in raw data and dropped |
| Stop while waiting (`build/stoptest`) | clean end, about 2.8 s |
| sigrok-cli killed while armed, then scan | found in about 1 s (after the resync fix) |

Note: changing RTS and DTR together passes through intermediate states
(two separate ioctls about 200 µs apart), which a pattern trigger can
legitimately catch. The test sequences change one line per step.

| Untriggered capture (EXT-low trick), UART decode | immediate; also with PulseView's `921600/8n1` serialcomm |
| PulseView 0.4.2 GUI | connect, untriggered and triggered runs, UART decoder all work |

PulseView passes its own serialcomm (`921600/8n1`); the driver adds
`dtr=1/rts=1` when the string doesn't set them.
